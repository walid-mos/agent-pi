# Standing budget

Extends [Before a job](SKILL.md#before-a-job). The amount in [`scripts/budget`](scripts/budget) applies per UTC calendar day to the whole Boat account, including all pots and the Mac. Count VM time at list price even when the plan covers it. Start eligible heavy jobs, full end-to-end suites first, without asking. Keep Boat's live billing, size, start and concurrency limits in force.

For one fresh VM, multiply its explicit TTL in hours by the current hourly price for the selected size. Round this maximum runtime cost up to six decimal places. From the same pricing page, take the highest published hourly rate across all sizes to cover earlier usage even if the account changed plans. After preparing the source and setup, run `~/.pi/agent/skills/boat/scripts/budget MAXIMUM_RUNTIME_DOLLARS --highest-hourly-dollars HIGHEST_HOURLY_RATE`. In a pot, use the vault prefix from [Before a job](SKILL.md#before-a-job). Use the same account scope as the launch. The check reads `boat --no-update limits --all --json` and adds a conservative start fee to the runtime cost.

| Decision | Action |
| --- | --- |
| `fits` | Start one VM immediately. Run the check again if the launch is delayed or you change its size or TTL. |
| `over-budget` | Ask Walid for this start with the purpose, size, TTL, `maximumChargeDollars`, and `remainderDollars`. Recheck live provider limits before an approved start. |
| `busy` | Wait for the other VM to stop and its usage to appear, then check again. |
| `contended` | Shorten the job within a measured TTL or coordinate an exclusive start with the other launchers. Use `--serialized` only while all launchers are actually excluded until this job's usage is visible. |
| `provider-blocked` or command error | Report the refusal or missing evidence. Resolve it and reread limits before starting. |

`last24hUsageSeconds` includes today's metered compute and part of yesterday. Per-VM usage is size-weighted, while the rolling aggregate's size weighting is unconfirmed. The check takes the higher of the raw seconds priced at the highest hourly rate and the credit seconds divided by `creditSecondsPerDollar`. The aggregate covers compute. The check separately bounds recent extra-start fees by multiplying `starts.day.used` by the highest current `overagePrices.startBrackets` fee. It includes one more maximum fee for the requested start, since `nextStartDollars` can change before creation. This assumes the rolling start count includes all billed starts and the current bracket ceiling bounds their fees. Do not use the estimate if you know the fee schedule changed or the count is incomplete. [Boat pricing and units](https://docs.boat.dev/pricing.md) · [Start windows and fees](https://docs.boat.dev/limits.md#extra-starts)

The check defers while account-wide `activeSandboxes` or `liveUsageSeconds` is nonzero and reserves room for two starts that read an idle account at once. This assumes at most two jobs are between their check and becoming visible to Boat, all launchers use the check, and a stopped job's usage becomes visible before the next idle check. Coordinate all starts through one launcher if those assumptions cannot be maintained. Boat exposes neither a UTC-day fee total nor an atomic reservation, and a pot's `boat list --all` shows its own environment only. A third simultaneous start, metering lag, uncoordinated starts or separately billed features such as saved snapshots and the AI proxy can invalidate the estimate. Keep those paid features out of these jobs and reconcile known external charges before launching.
