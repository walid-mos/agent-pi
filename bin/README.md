# bin — pi-scoped shims

`infisical` delegates to `security/infisical-shim.ts`, supplies the machine token, checks the selected project before starting the CLI and refuses interactive commands. A refused project prints its name and the one-time human step. An unknown project ID prints a broken-link message. Authentication and project-link rules live in `skills/infisical/SKILL.md`. Claude Code must call this shim by its explicit path.

Pi prepends this dir first in PATH for the tools it spawns. Keep only what must
shadow a system binary or is pi-owned:

- `open` — thin delegate to the machine-wide rule in `~/.config/shims/open`
  (`dot_config/shims/open`): `.zshenv` prepends that dir, so every zsh session
  resolves `open` there; pi tool sessions hit this delegate first. Keeping the
  delegate makes tool coverage independent of how pi's parent shell assembled
  PATH.
- `tailnet-link` — symlink to the command of `skills/tailnet-links/scripts/`, so a
  pi tool session finds it on a machine where `tailnet-link setup` has not
  linked it into `~/.local/bin` yet.
- `agent-lifecycle` — symlink to the command of `skills/agent-lifecycle/scripts/`, so a
  pi session calls the lifecycle sweeper's `closed`, `reopen`, `keep` and `policy`
  by name.
- `syneva` — generated by the syneva pi extension; do not hand-edit.
- `fd`, `rg` — arm64 binaries shadowing/baking in brew versions for pi sessions.
- `pi-drift.ts` — `pnpm run drift`: fails when the running `pi` differs from
  `AUDITED_PI_VERSION` (`extensions/lib/ui/pi-runtime.ts`).
- `pi-token-sync` — on the Mac that signed in to Codex, refreshes through Pi's
  auth API and publishes access-only credentials to the bound vault entry.
  `pi-token-sync-install` replaces its existing hourly Mac job. See
  [Shared Codex authentication](#shared-codex-authentication).
- `pi-token-pull` — on every machine that did not sign in to Codex (the
  Pots desktops, the workspace VMs), copies the Codex access
  token the signed-in machine publishes in the vault into `auth.json`. Needs
  `INFISICAL_UNIVERSAL_AUTH_CLIENT_ID`/`_SECRET` in its environment and the
  vault binding `~/.config/agent-secrets/core-vault.json`.
- `chezmoi-reconcile` — on the dotfiles publisher, drops from the chezmoi source
  every managed target deleted live; a no-op on a consumer or without
  `dotfiles.json` (README, "Dotfiles roles"). Run at session start and stop
  by `extensions/commands/chezmoi-reconcile/` and by the Claude Code hooks in
  `~/.claude/settings.json`.
- `magpie-claude-token-sync` — on the machine hosting the Magpie gateway,
  reads `CLAUDE_CODE_OAUTH_TOKEN` from the vault location the binding names,
  registers it in Magpie through a temporary local `magpie web`, proves the
  account answers a request held to that account alone (a 5-minute gateway
  key, removed afterwards), then forgets every other `Claude setup-token`
  account. A failed proof leaves the older accounts in place, and Claude
  Code's own sign-in is never touched. Prints the account, the HTTP status and
  the removed names. The token stays in the child's environment and a loopback
  request body. Needs the machine identity in its environment, like
  `pi-token-pull`.
- `magpie-gateway-priority` — on the machine hosting the Magpie gateway,
  `check` fails when its launchd job is not `Interactive` and `fix` sets the
  type and reloads the job, restoring the file when the gateway does not
  answer afterwards; a no-op elsewhere. `check` runs at session start by
  `extensions/model/gateway-priority/`.

- `test-pace.ts` — Claude Code calls the shared test decision with its current transcript: `node --experimental-transform-types ~/.pi/agent/bin/test-pace.ts --session <JSONL> --intent <bug or requirement> <test paths...>`. It reads the human's requests, questionnaire answers and relays itself and prints `pace` (`bug`, `logic`, `none`) and `permission` (`new`, `existing`, `none`: the human consent covering every named path whose exchange allows the `--intent` as the operation, `operation.ts`). It sends no source code and does not mint Pi grants.
- `eval-test-pace.ts` — run through the core vault providers environment to calibrate the pinned pace, consent, operation, stop-target and scope-path questions, against the cases `test-pace-cases.ts` loads; a consent case may carry the agent `question` its reply answers, a stop-target case the `thread` a stop may cancel grants in, and a scope-path case the `path` its exchange writes. Expectations are agent-labelled. Each report separates false grants, unavailable calls and conservative refusals; any false grant, a missed withdrawal or stop included, or unavailable call fails the run.

Personal cross-context tools live in `~/.local/bin` (last in PATH on purpose),
not here.

## Shared Codex authentication

Run the publisher only on the Mac whose `~/.pi/agent/auth.json` contains the
refresh-bearing `openai-codex` sign-in. Refresh tokens rotate. Keep that chain
on this Mac and never put it in the vault or copy its auth file to another
machine. Consumers receive only `{ access, accountId, expires }`, with expiry
in epoch milliseconds, at the location named by `binding.clients.pi`.

`pi-token-sync --publish` uses the public `ModelRuntime` API from the pinned
Pi SDK. `getAuth` refreshes under Pi's file lock and persists the rotated
credential before releasing it. The publisher uses the same auth file as Pi,
requests enough validity for two hourly intervals plus the puller's margin,
and reads the persisted result. It loads no `models.json`, sessions,
extensions or project settings. See Pi's installed `docs/sdk.md`, pi-ai's
README sections "Credential Store" and "OAuth Providers", and
`ModelRuntimeAuthOverrides` in its TypeScript declarations.

`pi-token-pull` requires more than five minutes of remaining validity, matching
Pi's default minimum. Expired, near-expiry and malformed publications exit
non-zero before changing local auth, with a publisher recovery command. A
consumer keeps other provider entries and never replaces its own
refresh-bearing sign-in. An already-running Pi process may need a restart
after a pull. The pull replaces `auth.json` atomically but does not take Pi's
credential lock, which the installed SDK exposes only for its own OAuth
refresh: if Pi rewrites `auth.json` for another provider in the same moment,
run the pull again.

### Install or repair the publishing Mac

Update `~/.pi/agent` to the commit from this pull request first. Use Node 24
and the dependencies installed by this checkout's package manifest. In a
shell that already exports this Mac's Infisical Universal Auth client ID and
client secret, run:

```sh
node "$HOME/.pi/agent/bin/pi-token-sync-install"
launchctl print "gui/$(id -u)/fr.nextnode.pi-token-sync"
```

The installer unloads `fr.nextnode.pi-token-sync` first and replaces
`~/Library/LaunchAgents/fr.nextnode.pi-token-sync.plist` in place. It checks
the two machine credential variables before unloading, so a shell that lacks
them leaves the current job running. It saves only those credentials in
`~/.config/agent-secrets/pi-token-sync.json`, owned by the user with mode 0600.
The job calls the installer's absolute Node executable and the versioned
publisher directly. It reads that private JSON with `--job`, without starting
zsh or sourcing `~/.cache/zsh/infisical.env`. Reinstall after changing the
machine credentials or the Node path.

Installation first runs the publisher with the job's credentials and a minimal
environment. It installs the schedule only after the vault readback matches
the publication. `first publication verified, hourly job installed` proves
that first write and readback succeeded. A failed installation exits non-zero
and can leave the old job unloaded. Repair the reported prerequisite and rerun.

To verify the scheduled execution, run:

```sh
launchctl kickstart "gui/$(id -u)/fr.nextnode.pi-token-sync"
launchctl print "gui/$(id -u)/fr.nextnode.pi-token-sync"
tail -n 5 "$HOME/Library/Logs/fr.nextnode.pi-token-sync/stdout.log"
tail -n 5 "$HOME/Library/Logs/fr.nextnode.pi-token-sync/stderr.log"
```

Wait for the job to finish before reading its last exit status. It must be 0,
and stdout must report `published and verified` with a future expiry. The
publisher prints no credential values. Then remove the pre-versioning copy at
`~/.local/bin/pi-token-sync`, if one exists, so the Mac has a single publisher.
The hourly schedule also runs when
loaded. The Mac must be awake and online to publish. Stale consumers fail
loudly when publication stops.

On each consumer with its own authorized machine identity and vault binding:

```sh
node "$HOME/.pi/agent/bin/pi-token-pull"
```

It must report `updated` or `already current` with positive validity. Keep the
existing consumer schedules. The external workspace profile and sandbox
integrations are maintained in their own repositories.

### Credential boundary and checks

The publisher, installed Pi SDK, binding, machine-credential file and Mac
account are trusted. Project files are untrusted input. The job starts Node
directly, loads no project code or shell profiles, parses credentials as JSON,
and sends the access-only publication in an HTTPS request body. Credentials
never enter command arguments or success logs. Failures suppress raw SDK,
JSON and network errors because those can quote credentials.

The Mac account's other processes can read its files, environment and memory.
This job does not isolate credentials from other processes with the same user
or from root. OpenAI and the bound vault are the network recipients.

`tests/codex-token-pull.test.ts` exercises expired and near-expiry publications,
fresh imports, preservation of local sign-ins and malformed publications with
an isolated home and fake network. Temporary homes are removed after each
run. The live `/clients/pi/PI_OAUTH_CODEX` entry is not used by these checks.
